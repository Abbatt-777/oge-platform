# Инструкция по разработке платформы — пошаговый план для Claude Code

**Источник требований:** `ТЗ_платформа_финальное.md` (разделы 1–18). Ссылки вида «раздел 7» ниже ведут туда.

**Источник интерфейса:** макет экранов на канвасе «Платформа ОГЭ — макет экранов». Макет покрывает кабинет ученика и административную панель. Кабинета преподавателя в макете нет — он собирается по образцу кабинета ученика (те же цвета, шрифты, компоненты), см. Шаг 14.

Эта инструкция заменяет предыдущую версию от 26.09.2026, составленную до появления преподавателей, групп, согласования расписаний и оплаты.

---

## Как работать с этим планом

**Один шаг за один заход.** Не просите Claude Code выполнить несколько шагов сразу. После каждого шага проверяйте результат по критериям «Готово» и только потом переходите к следующему. Объём вырос почти вдвое относительно первой версии — при попытке сделать всё сразу ошибки накапливаются незаметно.

**Модель.** Opus 5 для шагов с логикой и безопасностью (1, 2, 7, 8, 9, 12, 13), Sonnet для простых экранов и вёрстки — командой `/model sonnet`. Так квота расходуется разумнее.

**Порядок нарушать нельзя.** Шаги идут по зависимостям: расписание опирается на группы, группы — на аккаунты, оплата — на аккаунты и счета.

---

## Прежде чем начинать: три блокирующих решения

Из раздела 18 ТЗ. Эти три вопроса меняют структуру базы данных, поэтому Шаг 1 без них начинать не стоит:

1. **Состав анкет** ученика и преподавателя (раздел 4).
2. **Единица учёта часов** — занятия или часы, и как считается групповое занятие (раздел 9).
3. **Платёжный сервис** и юридическое лицо для приёма платежей (раздел 10). Это нужно не к Шагу 1, а к Шагу 15 — но подключение занимает недели, поэтому запускать процесс стоит сразу.

Остальные открытые вопросы из раздела 18 можно решать по ходу: в ТЗ для каждого зафиксирована редакция по умолчанию.

# ЭТАП 1. Основа

## Шаг 0. Подготовка проекта

Создать репозиторий и проект Next.js, подключить Supabase (авторизация, база данных, хранилище файлов), настроить деплой.

Положить в корень репозитория: `ТЗ_платформа_финальное.md`, эту инструкцию и файл `CLAUDE.md` следующего содержания:

```
# Проект: платформа подготовки к ОГЭ/ЕГЭ

Требования: см. ТЗ_платформа_финальное.md. Читать перед каждой задачей.

## Стек
Next.js (App Router), Supabase (Postgres + Auth + Storage), shadcn/ui + Tailwind, деплой на Vercel.

## Правила
- Кабинеты ученика и преподавателя — мобильный приоритет (390px базовая ширина).
- Админ-панель — десктоп (1280px).
- Все проверки прав доступа — на сервере, а не скрытием элементов интерфейса.
- Время хранится в UTC, отображается в часовом поясе пользователя.
- Никаких данных банковских карт в базе.

## Оформление
Фон #F6F1E7, текст #211F1C, синий акцент #24344A, янтарный акцент #C97A2E,
границы #E4DCC9, приглушённый текст #6B6559.
Шрифты: PT Serif (заголовки), IBM Plex Sans (текст).
```

**Готово:** пустой проект открывается по рабочей ссылке, подключение к базе работает.

## Шаг 1. База данных

Создать все таблицы по разделу 15 ТЗ (21 сущность). Не упрощать: `LessonParticipant`, `ScheduleApproval`, `AuditLog` кажутся необязательными, но на них держатся разграничение доступа и учёт часов.

**Готово:** все таблицы созданы, связи между ними работают, тестовые записи создаются и читаются.

## Шаг 2. Разграничение доступа на уровне базы

Настроить политики доступа по матрице из раздела 2:

- Ученик: только свои документы, счета, попытки, занятия (через `LessonParticipant`), состав своих групп.
- Преподаватель: только свои занятия, свои группы, ФИО своих учеников. Без доступа к документам, счетам и полным контактам.
- Администратор: всё.

**Готово:** запрос от имени ученика А не возвращает данные ученика Б; запрос от имени преподавателя не возвращает документы и счета. Проверяется запросами к базе, а не глазами в интерфейсе.

## Шаг 3. Вход и создание аккаунтов

Вход по коду подтверждения на почту или телефон, без пароля (раздел 4). Самостоятельной регистрации нет.

Администратор создаёт аккаунт с базовыми данными: ФИО, дата рождения, телефон, почта, город, роль. Пользователю уходит письмо-приглашение со ссылкой на вход.

**Готово:** обычный пользователь, вбив адрес админки вручную, получает отказ от сервера. Приглашение приходит на почту и ссылка работает.

## Шаг 4. Согласие на обработку ПДн

Экран согласия при первом входе (раздел 14): пользователь не попадает в кабинет, пока не отметит согласие. Факт согласия сохраняется с датой, временем и версией текста.

Страница политики обработки ПДн доступна без авторизации, ссылка в подвале всех страниц. Текст политики предоставляет заказчик — до его получения ставится заглушка с явной пометкой.

**Готово:** без отметки согласия кабинет не открывается; факт согласия виден в базе с версией политики.

## Шаг 5. Анкеты

Анкета ученика и анкета преподавателя по разделу 4 — разный состав полей для разных ролей. Пользователь заполняет сам после первого входа, редактирует в любой момент. Администратор видит и правит.

**Готово:** ученик видит анкету ученика, преподаватель — анкету преподавателя; обязательные поля нельзя пропустить.

## Шаг 6. Программы, темы, материалы

Программы → темы по порядку → материалы трёх видов (файл, ссылка, текст), несколько на тему (раздел 11).

Экраны макета: **«Мои программы»**, **«Темы программы»**.

**Готово:** неназначенная программа не видна ученику ни в списке, ни по прямому адресу; в тему можно добавить несколько материалов и задать порядок.

# ЭТАП 2. Документы

## Шаг 7. Документы: загрузка и проверка

Раздел 5 ТЗ. Четыре статуса: не загружен → загружен → подтверждён либо отклонён с причиной.

Администратор публикует шаблон PDF для конкретного ученика, ученик скачивает, загружает скан, администратор подтверждает или отклоняет.

Ограничения: PDF, JPG, PNG, до 10 МБ, понятное сообщение при превышении.

Экран макета: **«Документы»** (в нём уже показаны статус «Отклонён» с причиной и кнопка «Загрузить заново»).

**Готово:** прямая ссылка на файл договора не открывается в приватном окне браузера без входа в аккаунт. Это ключевое требование раздела 14 — проверять обязательно. Преподаватель не имеет доступа к документам ни через интерфейс, ни через прямой запрос.

# ЭТАП 3. Расписание — ядро системы

Самый объёмный и самый рискованный этап: в нём вся логика состояний. Закладывайте запас по времени.

## Шаг 8. Группы и закрепление преподавателей

Раздел 6 ТЗ. Создание групп (название, программа, преподаватель, предельный размер, состав), закрепление преподавателя за группой или за индивидуальной связкой «ученик — программа».

Замена преподавателя: непроведённые занятия переходят к новому и требуют согласования заново; проведённые остаются в учёте прежнего.

**Готово:** ученик может одновременно состоять в группе и иметь индивидуальные занятия; при замене преподавателя статусы занятий пересчитываются правильно.

## Шаг 9. Формирование расписания

Раздел 7 ТЗ. Администратор создаёт занятия пакетом: группа или ученик, преподаватель, даты и время. Длительность не более 40 минут.

Проверка пересечений: у преподавателя и у каждого участника не должно быть двух занятий в одно время — предупреждение с указанием конфликтующего занятия.

Все даты в UTC, отображение в часовом поясе пользователя.

При создании занятия формируется список участников (`LessonParticipant`): один ученик для индивидуального, состав группы для группового.

**Готово:** попытка поставить преподавателю два занятия на одно время даёт предупреждение; занятие длительностью 45 минут сохранить нельзя.

## Шаг 10. Согласование преподавателем

Раздел 7 ТЗ, семь статусов занятия. Пакет приходит в кабинет преподавателя со статусом «на согласовании». Преподаватель согласовывает пакет целиком одной кнопкой либо отклоняет отдельные занятия с указанием причины.

Отклонённое возвращается администратору с комментарием.

**Готово:** несогласованное занятие ученику не видно ни в кабинете, ни по прямому запросу к базе. Это главная проверка шага.

## Шаг 11. Публикация ученику и письма

После согласования занятия появляются в кабинетах участников, и каждому уходит письмо с расписанием: предмет, дата, время в его часовом поясе, длительность, преподаватель, формат.

Экран макета: **«Расписание»**.

**Готово:** два участника в разных часовых поясах получают письма с корректным для каждого временем.

## Шаг 12. Ссылки на занятия

Раздел 8 ТЗ. В день занятия администратор вставляет готовую ссылку, занятие переходит в статус «Ссылка направлена», кнопка «Подключиться» появляется у преподавателя и всех участников одновременно.

**Готово:** до добавления ссылки кнопки «Подключиться» нет; после добавления она есть у всех участников; замена ссылки до занятия работает.

## Шаг 13. Отметка о проведении и учёт часов

Раздел 9 ТЗ. Преподаватель отмечает занятие проведённым; администратор может поставить или снять отметку. Каждое изменение записывается в журнал (кто, когда).

Расчёт по формулам раздела 9: отработано занятий, отработано часов, осталось занятий, осталось часов. Отменённые и отклонённые не считаются.

**Готово:** цифры сходятся вручную на тестовом наборе из 5 занятий; при отмене занятия счётчик отработанных не меняется.

## Шаг 14. Кабинет преподавателя

Собирается из уже сделанного: расписание с согласованием (Шаг 10), список групп и учеников, свои часы (Шаг 13), отметка о проведении, анкета (Шаг 5).

Макета нет — вёрстка по образцу кабинета ученика: те же цвета, шрифты, нижняя навигация, мобильный приоритет.

**Готово:** преподаватель видит только свои занятия и своих учеников; документы и счета учеников недоступны.

# ЭТАП 4. Оплата

## Шаг 15. Счета и онлайн-оплата

Раздел 10 ТЗ. Администратор выставляет счёт (сумма, назначение, срок), счёт появляется в кабинете ученика, ученику уходит письмо, ученик платит через платёжный сервис.

Два требования безопасности, которые нельзя упрощать:

- Данные карт не проходят через платформу — ввод на стороне сервиса.
- Статус «Оплачен» ставится **только** по серверному уведомлению от платёжного сервиса, а не по возврату пользователя на страницу успеха. Иначе статус подделывается переходом по ссылке.

**Готово:** ручной переход на адрес страницы успеха не меняет статус счёта. Это и есть главная проверка шага.

# ЭТАП 5. Задачи и отчёты

## Шаг 16. Интерактивные задачи по математике

Раздел 11 ТЗ. Два типа ответа (число или выбор варианта), мгновенная обратная связь, объяснение показывается в обоих случаях, неограниченные повторы, сохранение каждой попытки.

Числовой ответ принимает и запятую, и точку.

Экран макета: **«Задача по математике»** — там это поведение уже реализовано, можно брать логику оттуда.

**Готово:** после неверного ответа можно ответить снова; все попытки, включая неудачные, видны в базе с датой.

## Шаг 17. Административная панель целиком

Раздел 12 ТЗ. Семь разделов: Ученики, Преподаватели, Программы, Группы, Расписание, Документы, Оплата.

Главная страница: занятия на сегодня и статус ссылок, занятия в ожидании согласования с выделением просроченных, документы на проверке, просроченные счета.

Отчёт по часам преподавателей с фильтром по периоду и выгрузкой в файл — прямое требование заказчика.

Экран макета: **«Админ-панель»** (в макете 4 вкладки из 7, остальные делаются по тому же образцу).

**Готово:** отчёт по часам сходится с данными из Шага 13; каждое действие проверяется по роли на сервере.

# Перед запуском

- Пройти весь путь ученика и преподавателя с реального телефона, а не в уменьшенном окне браузера.
- Проверить, что чужие файлы, занятия и счета недоступны (разделы 2 и 14).
- Проверить, что статус оплаты нельзя подделать (раздел 10).
- Настроить ежедневное резервное копирование и **проверить восстановление** — до запуска, а не после первой потери данных.
- Разместить тексты политики ПДн, согласия и договора, полученные от юриста (раздел 14).
- Подтвердить, что размещение серверов соответствует требованиям к хранению ПДн (разделы 14 и 16).
